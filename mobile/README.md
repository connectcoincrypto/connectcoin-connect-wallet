# ConnectWallet mobile development alpha

Android and iOS development targets, isolated from desktop and installed as `com.connectcoincrypto.connectwallet.mobile.alpha`. Version `1.0.0-alpha.1`, English UI. The desktop build remains unchanged. The native iOS app, build instructions, platform differences and acceptance limits are documented in [ios/README.md](ios/README.md).

## Android reference feature set

The detailed behaviors in this section describe the Android reference implementation. iOS shares the packaged UI and transaction/vault formats, with native Swift/C++ implementations; Android Activity, document-provider and foreground-service behavior must not be assumed to apply to UIKit. See the iOS notes for its foreground-only claims, document picker, lifecycle and verification status.

- **General settings:** a separate Settings screen is accessible before unlocking, with Dark/Light/System appearance, a public DNS hostname and TCP port for the mainnet RPC server, and an optional native inactivity timer. Defaults are Dark, `connectcoin4.com:48190`, and **0 minutes: never auto-lock while the app is active**. A positive duration from 1 to 1,440 minutes counts real native touch/key activity, including confirmation dialogs, not RPC traffic or claims. Backgrounding still locks the wallet. Settings are saved as one native preference record. A server change requires native confirmation of the endpoint, refuses active wallet recovery/operations or unsettled claims/broadcasts, locks the wallet, replaces both query and subscription connections, and revokes previous endpoint reads, cursors and funding selections. Claims do not start automatically; existing unknown-outcome receipts and RPC quotas/cooldowns are retained. Public display caches are scoped by endpoint and wallet identity. Theme/timer-only changes do not reconnect or re-scan the wallet. Native dialogs follow the selected appearance too.
- **Spend verified addresses during balance sync:** after native HD address discovery is complete, each fully loaded history/UTXO address can join an explicitly partial balance after replaying its original journal checkpoint. Remaining addresses continue loading with the same 16-worker and per-minute limits. Send and P2C may use only the verified, funded subset; **Use all verified balance** freezes that source-address selection instead of silently including addresses found later. Native preparation independently re-reads and authenticates those funds, so its own checks can still wait for RPC quota. Saved display data is never spendable, partial balances never replace the complete persisted snapshot, and cancellation/reorg/failure revokes partial availability. No server change is required.
- **Startup reuse and display cache:** recovery captures existing `getaddresschanges` checkpoints before each rolling group of history reads. The public first pages are reused by the initial balance/history load; original cursors and journal replay reconcile changes during recovery. Fully empty recovered histories avoid redundant history/output queries. Reorgs or expired retained cursors cause one fresh-baseline retry. Recovery cache is memory-only, bounded to 8 MiB and cleared on lock/rescan. The last validated public balance plus up to 200 activity entries is saved separately by mainnet wallet identity (2 MiB maximum); startup may display it explicitly as previously saved, never as freshly verified or spendable. Baseline loading shows completed/total addresses. Existing RPC methods, 16-way concurrency and per-minute quotas remain unchanged; no server upgrade is required. A first scan of a large wallet can still wait for the existing quota.
- Native BIP39/BIP32 mainnet wallet creation/import/unlock, libsecp256k1 Schnorr signatures, and the desktop-compatible scrypt/AES-256-GCM envelope. Recovery words/passwords use native dialogs, not JavaScript, Preferences or clipboard. Vault storage is atomic, app-private and excluded from Android backups.
- **Security & backup:** Settings offers **Change wallet password** and **View recovery phrase**. Both require the current password in native dialogs, even when already unlocked; neither sends secrets through JavaScript or RPC. Password change first locks the wallet and revokes old HD encryption writers, preserves the full recovery/HD payload, and uses fresh salt and nonce at the existing scrypt cost. Serialized atomic writes are read back; failures restore and verify the original snapshot, or explicitly require retaining both passwords if storage cannot be verified. Export a new encrypted backup afterwards: old backups still use the old password. Viewing recovery does not unlock or modify the wallet; the numbered phrase and any existing BIP39 passphrase stay in a native window that clears on dismissal, backgrounding or after 60 seconds. Screenshots remain allowed under the existing policy. Physical-device acceptance testing is still required.
- Creation and recovery use an empty BIP39 passphrase, matching desktop; there is no extra passphrase field. Opening an existing encrypted alpha vault or importing an encrypted wallet file honors its saved passphrase without changing its keys. Phrase-only import does not support nonempty BIP39 passphrases.
- Creation has three native steps: read the 24 numbered recovery words, confirm selected words (with a way back to review the same phrase), then choose the local encryption password. Switching apps preserves unfinished creation/import steps, words and inputs in Activity memory only. No wallet is saved before final confirmation. Explicit cancellation, lock, or Activity/process destruction discards the draft; returning after destruction starts over. Once encryption/saving begins, the usual background cancellation checks apply.
- **Encrypted wallet files:** **Export wallet file** saves the existing password-encrypted vault with Android's document picker and verifies the saved bytes. It works with a locked wallet and does not expose recovery words, passwords, ciphertext or file URIs to JavaScript. The startup screen has separate **Import recovery phrase** and **Import wallet file** actions: the first opens native recovery-word entry, while the second imports an encrypted file without an intermediate chooser. File import asks for its existing password in a native dialog, authenticates and validates the mainnet vault, preserves its passphrase/HD indexes and metadata, then requests fresh address recovery. Desktop-compatible wallet files keep the scrypt/AES-256-GCM format and cost. Reads are size-bounded; document-provider operations have cancellation and deadlines. Export is a point-in-time wallet backup, not a backup of app settings, public payment receipts or a guarantee that a cloud provider will retain the file. Keep the file and its password safely; neither replaces the other.
- **Replace after backup:** Create wallet, Import recovery phrase and Import wallet file remain available when a native wallet already exists. A native confirmation first requires saving its existing encrypted envelope through Android's document picker and reading it back byte-for-byte. Keep that backup and its original password (the envelope can be opened in ConnectWallet desktop), as well as the recovery words. The original vault remains in place through setup; the final replacement checks that it still matches the backup. Cancelling or failing before replacement leaves the original vault intact. Successful replacement stops Automatic Claims and clears payment drafts; it does not transfer any funds or start claims for the new wallet. Backup authorization is memory-only and cannot survive Activity/process recreation. Public outgoing receipts and reserved-input safeguards remain stored internally, but the global **Last outgoing transaction** card is not displayed.
- **Native HD recovery:** desktop-compatible `m/44'/0'/0'/{0,1}/{index}` receiving/change branches, including spent-only history. Imported and older alpha wallets scan both branches through 20 consecutive unused addresses, preserving issued indexes. Discovery and public/payment baselines use rolling windows of up to 16 address reads; discovery commits gap decisions in index order even when replies arrive out of order. The native transport pipelines these queries over one reused TCP connection, rather than opening a socket per address. This overlaps client work and avoids waiting between requests; the current server still processes each connection's requests serially. Incomplete recovery cannot enable payments or publish a partial wallet balance. The explicit 10,000-address resource guard reports incomplete recovery instead of omitting funds. **New address** persists its receive index before display; change allocation persists before broadcast, including unknown outcomes. New addresses and metadata use the existing encrypted envelope with fresh AES-GCM nonces; the derived update key is native-only and wiped on lock. Previously issued addresses remain valid. A mnemonic alone cannot discover activity beyond an unused gap of 20, matching desktop's gap rule.
- Native payment review of recipient, entered amount, recipient's net amount, mining fee, change and pending conflicts before signing. **Send** supports **Use all balance**, which fills the available confirmed balance and enables **Deduct fees from payment**, plus a per-payment fee rate from 1,201 to 100,000 connects/vB (default 1,500). Use-all excludes immature, pending and reserved coins; native review compares its displayed snapshot with freshly selected funds and refuses changes rather than silently increasing the spend. Pasting a new payment clears deduction/use-all, editing the amount clears use-all, and refreshing never rewrites the draft amount. Tiny-change top-ups are shown separately from mining fees. Immutable native policy is checked before review and signing; exact typed ConnectCoin serialization and parent/ownership checks remain. One recipient, up to 50,000 scanned output records, and a 1 CONN aggregate fee ceiling. The 400,000-weight-unit transaction limit allows up to 1,738 ordinary inputs for a one-output sweep (1,737 with change; P2C depends on its output size). Persisted public broadcast receipts protect indeterminate submissions; no arbitrary raw signing/broadcast bridge. These Send options do not change P2C or Automatic Claims fees.
- **Oversized ordinary payments:** Send automatically plans up to 32 independently standard transactions when a fragmented payment exceeds the single-transaction weight limit. The native confirmation shows the count, aggregate recipient amount, fees and change before authorizing the batch. Parts use disjoint confirmed, mature, unreserved original inputs, never the preceding part's unconfirmed change; any change appears only in the final part. Added/deducted fee and use-all semantics apply to the aggregate, without silently omitting funds. Native parent/ownership and fresh inventory checks still apply per part and to the full selected union. All signed public transaction IDs/bytes and reservations are saved before transmission. Submission is sequential and stops on failure, cancellation or uncertain outcome; batches are not atomic and never auto-rebroadcast. A dedicated Send-only result retains every part across restarts and blocks new transfers until explicitly acknowledged. Acknowledging does not spend, resend or release uncertain reservations. No global outgoing-transaction card returns, no blockchain limits change, and no Core/server deployment is required. Bounded funding memory, quota waits and the existing native review deadline remain; uneconomic/dust batches fail explicitly.
- **Batch crash recovery:** reading a saved result locally also reconciles reservations left by an interrupted app process. Only exact inputs belonging to parts durably marked **not-sent** can be released, and only while no native submission is active. Submitted, uncertain and differently owned reservations remain held. Recovery never sends or retries a transaction.
- **Fragmented claim balances:** selection uses amounts before downloading only the selected parents. Fully parsed, txid-authenticated parent data is kept in a bounded memory cache without witnesses; each selected output's amount and ownership are still checked. Fee sizing and shared signature hashes avoid quadratic work. A `getaddresschanges` watermark plus journal replay reconciles the live UTXO pages, including mutations behind pagination cursors; ordinary blocks no longer restart the baseline. Incremental readbacks recheck the same selected inputs after downloads and again after native confirmation, before signing. First preparation can still take minutes under server quotas; progress is shown and Lock cancels it. Explicit read-only quota/capacity errors are retried within a 15-minute attempt budget, never broadcasts. If the budget expires, another Review resumes cached parent downloads in the same app process. Snapshot retries, pagination, memory and retained reservations remain bounded; this is not unlimited consolidation.
- **P2C creation:** a dedicated **Pay-to-Connect** section, separate from **Send** and **Automatic Claims**, accepts an ASCII/punycode public domain, a CONN reward and an exact expected-candidate count (1 through 2^256). A restricted native review validates these fields, derives the work target, verifies funding and displays the domain, public reward, signature policy, fee and change before signing. After funding verification, an advisory native RSA probe contacts a public endpoint on port 443 with a 3-second DNS-inclusive network budget. Only a completed TLS 1.3 handshake with consensus-verified certificates and signatures selects RSA-PSS-only mask 6; failure, timeout or unavailability leaves all supported schemes (mask 7) allowed, with an explicit native review result. Root bundle version 1 is fixed, probe randomness is independent of wallet keys, and no mining target must be reached. Cancellation/lock/backgrounding cannot turn a late probe into a confirmation or broadcast. A successful check confirms only one server's current capability, not future availability or every server behind the domain; an unsuccessful check does not prove incompatibility. This funds a public bounty collectable by any eligible claimer, not a payment to the website owner. The form links to Automatic Claims without starting it, and ordinary-address payment drafts stay separate.
- Balance/history combine all recovered native-owned addresses; receive URI/QR follows the selected receiving address, with desktop-compatible numeric/text limits. Wallet identity remains stable when that address changes, so Send drafts are preserved. There is no public-address tracking mode. A pre-baseline journal watermark reconciles live pages atomically; later changes normally require only journal deltas, not downloading every address again. History deduplicates transaction IDs and sums net flows across wallet addresses, including self-transfers and change. Display is capped at 2,000 entries; the underlying validated balance inventory is separate and bounded, never silently truncated. Each native input is signed with its own authenticated derivation path.
- Activity rows open transaction details: current status/confirmations, transaction ID, confirmed block height/hash, involved wallet addresses, and exact combined received/spent/net amounts (not an inferred fee). Details follow validated history and tip updates, show stale state when disconnected, and close if the wallet or selected entry disappears. Opening details performs no RPC calls. **Open in explorer** explicitly launches the system browser through a txid-only native bridge pinned to `https://explorer.connectcoincrypto.com/tx/`; it does not navigate the wallet WebView or authorize a payment.
- **Paste payment link** reads plain clipboard text through the foreground Android bridge only after a button click, rather than relying on WebView clipboard permissions. Both bare mainnet `cc1p` addresses and `connectcoin:` payment links are validated before changing the draft; malformed checksums, other networks and unsupported instructions remain rejected. Clipboard failures fade below the button, and late results cannot overwrite a changed draft. Send/P2C show **Unlock native wallet** when locked and **Lock** when unlocked; a pending native operation can still be cancelled.
- **Scan payment QR** opens a bundled QR-only camera scanner after an explicit button click. Camera permission is requested only then; images are not saved or uploaded. Android also opens external `connectcoin:` payment links, whether the app is starting or already open. Both paths accept only validated mainnet payment data (up to 1,024 characters), display label/message as plain text, and automatically fill the Send form, replacing any previous draft without an extra acceptance step. If the app/account is unavailable or a native operation is in progress, only the latest request waits in memory and is filled automatically once the form is available. A transaction already under native review is never changed. No link or scan starts signing, broadcasting, claims, or unlocking. A camera-induced pause keeps the existing native wallet locking policy; unlock again if required before review. Camera and external-intent behavior still require validation on a physical device.
- **Live balances and confirmations:** one separate foreground-only native TCP channel registers `subscribeaddress({address, changes_only: true})` for owned addresses and one `subscribetip`. It requires explicit changes-only acknowledgements. The current server allows 100 subscriptions per IP; mobile watches up to 99 addresses plus the tip and explicitly shows limited coverage (including shared-IP capacity limits). Manual Refresh checks the complete wallet even when some addresses cannot be watched. Ordinary tips only project confirmations locally, without balance/history/UTXO queries. Address changes, including coinbase maturity, trigger validated journal reconciliation. Pages are bounded to 512/address, 20,000 rows/address/type and 200,000 total rows; exceeding a bound fails explicitly, marks any earlier partial snapshot stale and never presents an incomplete address as verified.
- Startup/resume, registration/reconnection, Send/P2C results and explicit refresh still catch up independently. A lost established subscription, reorg or resynchronization request invalidates old-chain reads and confirmation projection until a fresh history snapshot is validated. Native lifecycle and connection-generation checks discard stale events; coalescing retains address/reset hints even when ordinary tips arrive afterward. A change during a read retains one follow-up, failed reads retry with backoff, and there is no periodic balance polling when nothing changes. The quiet channel's tip heartbeat checks liveness only and never refreshes balances. The channel stops in the background/offline and reconnects automatically without occupying the query/claims socket workers. Routine address refreshes keep the last validated amount usable; explicitly stale/offline data remains unavailable. Notifications never rewrite a payment draft or authorize signing. A compatible changes-only JSON-RPC server is required (already deployed on the default endpoint).
- Native P2C capture and certificate/proof validation reusing pinned Core consensus code, immutable roots and patched MbedTLS. Independent saved ceilings for connection starts/second and simultaneous captures (1–100 each, default 100). Progressive bounded discovery and preparation run separately from captures; parent RPC results are reused. Domain selection alternates round-robin and highest estimated return, always choosing the best eligible output within a selected domain. Priority uses exact signature-mask EMA, the desktop's stable randomized factor and raw minimum-return floor; bounded recovery probes retry below-floor policies at most once per minute. Scheduling turns are reserved at dispatch so a pending DNS/TCP start cannot block every other domain or reorder turns when acknowledgments arrive out of order. Recovery policies are reserved separately; their cooldowns and attempt counters begin only when TCP actually starts. Parallel attempts for one bounty share a single winning submission, and broadcasts are serialized with a durable unknown-outcome guard.
- Within each domain, IP selection maintains separate success/time EMA for each IP and signature mask, with 99% performance weighting and 1% uniform exploration. DNS refresh preserves statistics for unchanged IPs. EMA starts at success 0.1/time 0.02 seconds and updates with 0.999 history + 0.001 observation. Certificate/signature validity counts independently of reaching the target; an expired operation can report that verification succeeded without making its proof eligible for broadcast. Handshake capture budgets remain separate from valid-proof statistics.
- Real claims counters: attempts, valid/invalid proofs, target hits, submitted/unknown transactions, connection rate, eligible bounties, discovery progress and current domain. Actual connections/second uses timestamps of real TCP starts in the last 10 seconds, divided by 10, not the lifetime session average. The timestamp deque handles out-of-order acknowledgments and expires old starts even while paused/stopped; a new run clears it. The fixed window ramps up during the first 10 seconds and returns to zero after 10 seconds without starts.
- Claims connection ceilings are configurable from 1–100 starts/second and 1–100 simultaneous attempts, with both defaulting to 100. Apply limits saves native preferences without starting claims; changes also apply while running. Active connections and actual measured rate are separate counters. High settings may increase battery/data usage, and neither ceiling guarantees that throughput.
- Dispatch and native TCP-start timing each use an engine-wide schedule: after each admission/start, `next = max(next + ceil(1 second / configured_rate), now - 1 second)`. The following wait uses the remaining time to that deadline, never a fresh full interval. Short delays are recovered while work is waiting; timing debt is bounded to one second, independently of the configured rate. Genuine idle and lifecycle interruptions discard overdue phase credit, never the rolling one-second start history. The native gate separately enforces the configured rolling one-second ceiling even during catch-up, stop/start and rate changes. Only the FIFO head waits for the next native pacing deadline; cancellation/rate changes wake the affected waiters. Catch-up gaps may be shorter than `1/rate`, but idle time does not accumulate credit. Pending DNS, TLS and proof verification still consume bounded capture slots. Repeated start-acknowledgment scans are bounded, while capture completion/destruction always records any real start before releasing its handle.

- Pre-TCP timeout, busy and context failures release their capture slot without pausing every bounty of the same domain/signature policy. Further attempts still obey the configured start rate and concurrency; these local failures do not fabricate failed-proof EMA samples. DNS failures retain their short two-second retry delay.
- **Claims RPC recovery:** transient discovery/catalog/funding read failures retry independently while already validated bounty data remains fresh. Complete block indexes and delta replays are published atomically; partial responses never replace the working catalog. New proofs and broadcasts pause when that catalog is more than 60 seconds old, without cancelling a transmission already in flight. Read failures cannot trigger a broadcast retry or turn a pending transmission into an unknown outcome by cancelling it. Explicit Stop, lifecycle cancellation and the durable unknown-outcome guard remain separate. Diagnostics identify the failed RPC method, phase, elapsed/queued time and bytes received, without displaying parameters, addresses, transaction bytes or untrusted server messages. Existing RPC timeouts and configured capture rate/concurrency ceilings are unchanged.
- **Local RPC quota pacing:** Android waits for the local allowance before writing a request instead of raising `-32029`. Quota waits occupy no request worker and do not consume the network timeout. One persistent query TCP connection supports at most 16 in-flight operations; all pending/queued operations share a 48-job bound, leaving headroom when UI and native payment baselines overlap. The address/tip listener remains a separate connection. Per-minute allowances remain 48 requests per ordinary method, 6 `gettransactions` batches, and 8 `getblockbounties` calls per block hash with 48 total bounty calls. Allowances are reserved atomically immediately before writing, and server cooldowns are honored; 16 in-flight requests do not raise the per-minute quota. Other methods can proceed while one method waits. Cancelling an already-written query keeps its slot until its bounded reply is drained, without disconnecting unrelated queries or payments. Queued claims remain pending, and other eligible captures continue while their catalog is fresh. Stop or a stale/spent/invalid bounty cancels a queued claim only if the transport can prove no write occurred; the durable receipt becomes `not-sent` before the output is made eligible again. Already-written transactions are never automatically retried, and server errors/unknown outcomes retain their safety handling. Payment preparation keeps its shared 15-minute budget and lifecycle cancellation while waiting; local quota waits are not mistaken for a second, caller-side RPC timeout.
- A normal payment cancelled while still waiting to transmit also records `not-sent`. Only transport-proven pre-write cancellation can roll back that payment's reservations, after saving its receipt; reservations for older uncertain payments overwritten by a replacement are restored, not discarded. Storage failure keeps conservative check-required handling. Already-written or otherwise uncertain payments never release their reservations through this path.
- Mobile-data and background opt-ins default off. Native network policy treats metered/unknown connectivity conservatively. Explicit user Start only; no boot receiver, sticky restart or invisible auto-start. Android background claims use an ongoing service indication with Stop, not permission for additional notifications. System interruption is still possible.
- Screenshots and screen recording are allowed, including recovery-word screens; keep any captures of recovery words private. Secrets remain native-only, the WebView file/content proxy is blocked, and no remote WebView origin or generic HTTP/cookie/file plugins are exported.

## HD discovery reconnection (Android and iOS)

Transient connection/time-out, capacity and rate-limit failures retry only the failed discovery reads, preserving validated progress, original checkpoints and cursors in the same in-memory scan. One shared recovery gate prevents a failed parallel window from producing a burst of retry probes. Backoff increases from 1 to 30 seconds with jitter, honors server cooldowns and stops after eight failed probe rounds; offline waiting does not consume that budget. Existing 16-way concurrency and per-method minute quotas stay unchanged.

The UI distinguishes scanning, waiting for network, retry countdown, stopped and locked states. `0 checked` means no contiguous address result has been validated yet, not that the wallet has no history. Lock, backgrounding and wallet replacement cancel the old scan; unlock/manual recovery starts a new scan. Invalid responses, expired journals and storage/resource failures require explicit recovery instead of being treated as connection errors. No payment or claim broadcast is retried by this mechanism, and no server deployment is needed.

## Important integration gates

By default, the native runtime uses the same **connectcoin4.com:48190** plaintext TCP JSON-RPC service as desktop. Settings may select another compatible mainnet server by public DNS hostname and TCP port; URL paths, credentials and IP literals are not accepted. No new listener or server deployment is required. RPC traffic is not encrypted or server-authenticated; address activity and public transactions can be observed, and responses can be modified in transit. Network/genesis, schema, transaction and ownership checks remain, but they do not authenticate the RPC server or fully verify blockchain consensus. Private keys stay local. This RPC transport choice does not change P2C TLS handshakes or certificate/proof validation.

This is development code, not a production release. Creating test keys offline is distinct from verifying the entire end-to-end wallet flow on a device. Managed Java strings/garbage collection cannot promise perfect erasure; mutable private buffers are wiped on lock, and the wallet locks when backgrounded. Claims need only a public reward address and may continue separately.

The app requests a larger Android heap for the unchanged desktop scrypt cost (about 128 MiB of working memory). Wallet encryption/unlock requires at least a 256 MiB application heap; unsupported devices fail rather than silently weakening the KDF. The request does not preallocate RAM or guarantee that every device supplies enough memory.

The Android foreground service uses an explicit `specialUse` declaration explaining P2C proof collection. This does not guarantee Google Play policy approval. See the [Android foreground-service rules](https://developer.android.com/develop/background-work/services/fgs/service-types#special-use). No CPU block-mining service is implemented.

iOS now has a Capacitor/Swift app host, native wallet/HD/payment/claims runtime, UIKit-only secret entry and native document/camera integrations. Its separate CI builds real unsigned Simulator/device `.app` bundles, runs Swift tests and a disposable offline Simulator UI smoke test. These are development artifacts, not signed IPAs, TestFlight or App Store releases. Claims run only while the iOS app is visible; there is no iOS background-claims entitlement or service. Biometric unlock is not implemented. Native document-picker, recovery and lifecycle flows still require physical-device acceptance on both platforms.

## Build and verify

Use Node.js 24+, JDK 21, Android platform 36, Build Tools 35.0.0/36.0.0, NDK 28.2.13676358 and CMake 3.22.1.

```sh
# repository root
npm ci
cd mobile
npm ci
npm test
npm run test:ui
npm run sync:android
npm run check:android
cd android
./gradlew --no-daemon --max-workers=2 :app:testDebugUnitTest :app:assembleDebug :app:assembleDebugAndroidTest :app:lintDebug :app:lintRelease
```

Windows packaging verification uses `scripts/build-android.ps1 -SdkRoot <sdk> -JavaHome <jdk>`. SDK and JDK may live under ignored `.tools/`; scripts do not change global Windows configuration. Debug APKs are test-signed. Release APKs are unsigned compilation checks, not installable releases. Never commit keystores or user wallets.

The `mobile-alpha` branch workflow builds Android, runs isolated emulator instrumentation and cross-checks public native proofs on Linux/macOS; it also compiles static iOS device/simulator libraries. It uploads temporary Actions artifacts only, without a tag, GitHub Release or store publication.

The separate `ios-wallet.yml` workflow handles the complete iOS app on macOS with Xcode 26+, including native static linking, Swift vectors, Simulator UIKit/WKWebView smoke tests and unsigned device compilation. See [iOS build and verification](ios/README.md). Merely adding a test does not establish that it passed: use the workflow result for the exact commit and retain its test report/artifacts.

`native/tools/check-provenance.mjs` verifies vendored Core sources. `native/tests/test_oracle.py` uses the pinned desktop verifier and ephemeral public test certificates on loopback, including ECDSA/RSA/PSS restrictions and invalid cases. Native/JVM and UI tests must not touch real wallets or send public transactions.

`npm run test:rpc` is an explicit optional three-query TCP integration probe for a well-known public test address. It never broadcasts. Instrumentation is only for a fresh isolated emulator; it refuses existing wallet/profile data rather than deleting it.

## Remaining acceptance work

Run lifecycle, keyboard, large-text, rotation, metered Wi-Fi/mobile/VPN transitions, background Stop and process-death tests on real Android devices. Measure KDF heap/battery/traffic without reducing security parameters. Verify native payment/claims operation against the existing desktop RPC, using dedicated test funds only with explicit user action. Do not call macOS static-library compilation an iOS app test.
